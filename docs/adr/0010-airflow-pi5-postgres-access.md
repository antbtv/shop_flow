# ADR-0010: Airflow на Pi5, доступ к Postgres и методика сверки

- **Статус:** принято (2026-10-02), ревью `architect`: принять с правками, правки внесены (5 блокеров, 13 желательных).
- **Контекст:** M4 закрывает FR-8 (ежедневная сверка Postgres ↔ ClickHouse), FR-9 (DQ) и NFR-5 (ретеншн) DAG-ами Airflow на Pi5 (NFR-2). Ограничения:
  - Память Pi5 по ADR-0004: scheduler 1152m, api-server 768m, dag-processor 512m, метабаза 256m, LocalExecutor, `parallelism` 2, задача ~340 МБ. Замер был на стенде memtest с `SimpleAuthManager` без логина. Узкое место Pi5 — CPU.
  - Postgres на ноутбуке опубликован только на `127.0.0.1:5432`. Образ `postgres` по умолчанию пускает `host all all all scram-sha-256`: после публикации на LAN к суперпользователю `shopflow` можно было бы подключиться с любого хоста по паролю.
  - Ноутбук на Wi-Fi (`wlo1`, сейчас `192.168.0.105` по DHCP, ufw выключен, есть VPN-интерфейс `amn0`), его выключают и могут уносить из дома. Pi5 работает всегда (NFR-6).
  - У Postgres и ClickHouse нет общего порядка событий: задержка `stg` p95 ~31 с, витрин ~148 с (итоги M3), допустимо до 5 минут (NFR-3). `inventory` меняется в каждом заказе, `orders` — при каждой смене статуса, поэтому в любой момент в пути десятки ключей.
  - Типы ClickHouse: `stg_orders.updated_at` и `stg_inventory.updated_at` — `DateTime64(3)`; `customers` и `products` лежат только как журналы версий (`stg_*_versions`, ADR-0009) без `updated_at` и `email`; `address`/`segment` не Nullable, Spark пишет `''` вместо `NULL`. У `order_items` нет `updated_at`, генератор её только вставляет.
  - Секреты только в `.env` (ADR-0007), IP в compose и конфиги не зашиваются (ADR-0003).
- **Решение:**
  - **Доступ Pi5 → Postgres.**
    - Postgres публикуется на `127.0.0.1:5432` и `${LAPTOP_HOST}:5432`. `LAPTOP_HOST` — LAN-адрес ноутбука в `.env` ноутбука, закреплённый DHCP-резервацией на роутере по постоянному MAC `wlo1` (рандомизация MAC в профиле NetworkManager выключается, как на Pi5).
    - На ноутбуке `net.ipv4.ip_nonlocal_bind = 1` (`infra/laptop/etc/sysctl.d/90-shopflow.conf`): без Wi-Fi или в чужой сети docker-proxy всё равно занимает порт, и контейнер Postgres (а с ним весь CDC) не падает при старте.
    - Подсеть сети compose ноутбука закрепляется в текущем значении (`10.10.4.0/24`, `docker network inspect shopflow_default`), чтобы `pg_hba` мог на неё ссылаться. Смена `ipam` пересоздаёт сеть, это `down` стека; делается один раз в 4.2.
    - Свой `pg_hba.conf` из шаблона `postgres/pg_hba.conf.template`: обёртка entrypoint подставляет `PI5_HOST` и `LAPTOP_COMPOSE_SUBNET` через `sed`, IP в git не попадают.
      - `local all all trust` — сокет внутри контейнера, как в образе по умолчанию (`docker compose exec postgres psql` в скриптах).
      - `host all all ${LAPTOP_COMPOSE_SUBNET} scram-sha-256` — Debezium, Spark-генератор и сам хост: подключения к опубликованному `127.0.0.1:5432` приходят через docker-proxy с адреса шлюза сети compose, а не с `127.0.0.1`.
      - `host shopflow recon_reader ${PI5_HOST}/32 scram-sha-256` — единственная строка для LAN. Трафик из LAN идёт через DNAT, исходный IP Pi5 сохраняется (проверка: `client_addr` в `pg_stat_activity`).
      - `host all all 0.0.0.0/0 reject`.
    - Роль `recon_reader`: `LOGIN`, `CONNECT` на базу, `USAGE` на `public`, `SELECT` на 5 таблиц CDC, `CONNECTION LIMIT 2`. `ALTER ROLE ... SET`: `default_transaction_read_only = on`, `statement_timeout = '300s'` (уточняется замером 4.15: таблицы PG растут без ретеншна), `idle_in_transaction_session_timeout = '60s'`, `idle_session_timeout = '5min'` (соединения-зомби после сна ноутбука не съедают лимит). Создаётся в `postgres/init` (новый том) и идемпотентным `scripts/create-pg-reader.sh` (на существующем томе init не запускается).
    - Роль `debezium`, слот и публикация не меняются. Логическая репликация матчится в `pg_hba` по имени БД, ключевое слово `replication` ей не нужно.
  - **Ноутбук недоступен ≠ расхождение.**
    - Первая задача DAG сверки — `PythonSensor(mode="reschedule", poke_interval=1200, timeout=7200, soft_fail=True)`, проверяет подключение к PG. В режиме `reschedule` сенсор не держит слот при `parallelism` 2; по таймауту он `skipped`, нижние задачи пропускаются.
    - Недоступность — только ошибка без `pgcode` (connection refused, timeout, no route). `28000`/`28P01` (hba, пароль), `53300` (лимит соединений) и прочие — `error`, задача `failed`: ошибку конфигурации нельзя двое суток принимать за «ноутбук выключен».
    - Последняя задача `report` (`trigger_rule="all_done"`) пишет итог в `dq_check_results`. При пропуске сенсора она пишет `source_unavailable` и смотрит предыдущий запуск DAG в `dq_check_results FINAL` (в Airflow 3 задачи не ходят в метабазу). Два запуска подряд `source_unavailable` — `AirflowFailException`.
    - Строка подключения: `connect_timeout=10`, `keepalives=1`, `keepalives_idle=30`, `keepalives_interval=10`, `keepalives_count=3`; у задач `execution_timeout`. Иначе уснувший посреди запроса ноутбук вешает задачу: `statement_timeout` серверный.
    - Расписание: `CronTriggerTimetable("0 20 * * *", timezone="Europe/Moscow")` (время, когда ноутбук обычно включён), `catchup=False`, `max_active_runs=1`, ручной запуск. Запуск, пропущенный из-за перезагрузки Pi5, не догоняется: следующий через сутки, ручной запуск по runbook.
    - DAG DQ и ретеншна в PG не ходят и работают при выключенном ноутбуке (NFR-6).
  - **Методика сверки.** Сверяются живые строки 5 таблиц: Postgres против `stg_orders`, `stg_order_items`, `stg_inventory` (`FINAL`, `is_deleted = 0`) и последней версии по ключу из `stg_customer_versions`, `stg_product_versions` (`argMax(..., version)`, `argMax(is_deleted, version) = 0`, без фильтра по времени).
    - **Проверка отставания.** Перед сверкой: если в PG `max(updated_at) >= T`, а в ClickHouse `max(event_time)` из `raw_events` `< T`, пайплайн стоит или догоняет (например, после раздельного перезапуска, NFR-6). Статус `lagging` (нарушение NFR-3, задача `failed`), сверка не выполняется: иначе каждый ключ стал бы расхождением.
    - **Отсечка `T`.** `T = date_trunc('second', now()) - 15 min` по часам Postgres (часы ноутбука), передаётся в ClickHouse литералом `toDateTime64('…', 6, 'UTC')`. Целая секунда даёт одинаковое сравнение с полями в мс и мкс. 15 минут = NFR-3 (5 мин) с тройным запасом.
    - **Бакеты — грубый фильтр.** Обе стороны считают в базе, наружу уходят только агрегаты: `bucket = pk % 256` (у `inventory` `(product_id * 1000 + warehouse_id) % 256`), по бакету `count()` и сумма отпечатков `h`. PG берёт строки с `updated_at < T` (`order_items` — с `orders.created_at < T`). ClickHouse применяет ту же отсечку там, где у него есть та же колонка (`stg_orders.updated_at`, `stg_inventory.updated_at`, `created_at` заказа для `stg_order_items` через `LEFT JOIN`, чтобы позиция заказа из карантина не пряталась), а журналы `customers`/`products` отдаёт целиком (уточнение 4.10: без отсечки каждая строка, изменённая за 15 минут, ломала бы свой бакет, и арбитраж выкачивал бы почти всю `order_items`; гонки по-прежнему разбирает арбитраж). Бакет без расхождений считается сошедшимся.
    - **Арбитраж по ключу.** Для бакетов с расхождением задача выгружает пары `(pk, h)` из ClickHouse, затем из PG — пары `(pk, h, updated_at)` тех же бакетов (1/256 таблицы на бакет), уже после запроса к ClickHouse. Ключ, которого нет в PG или у которого `updated_at >= T`, считается «в пути» и в `violations` не входит. Расхождение — ключ с `updated_at < T` в PG, которого нет в ClickHouse или у которого другой `h`. Ключи «лишний в ClickHouse» (удалённые в PG) перепроверяются через 10 минут: тумбстоун мог быть в пути. В `details` до 20 ключей каждого вида.
    - **Карантин.** Ключ «нет в ClickHouse» может законно лежать в карантине `stg` (ADR-0008). `details` подсказывает искать его в `raw_events` и дозаливать `backfill_from_raw.py`.
    - **Отпечаток.** `h` — первые 8 байт `md5` канонической строки как знаковое `Int64`, сумма в `numeric` (PG) и `sum(toInt128(h))` (CH).
      - PG: `('x' || left(md5(s), 16))::bit(64)::bigint` (big-endian). CH: `reinterpretAsInt64(reverse(substring(MD5(s), 1, 8)))`.
      - Строка: PG `concat_ws(E'\x1f', ...)` с явным `coalesce(x, '')` у Nullable текста; CH `concat` с разделителем `'\x1f'`. Целые как есть, `Decimal(10,2)` как целое `× 100`, время как целые миллисекунды эпохи UTC: PG `floor(extract(epoch from ts) * 1000)::bigint`, CH `toUnixTimestamp64Milli` (как в `scripts/check_pipeline.sh`). Тест 4.10 проверяет, что Spark и коннектор отбрасывают микросекунды, а не округляют.
      - Колонки:
        - `customers`: `customer_id`, `name`, `address`, `segment`;
        - `products`: `product_id`, `name`, `category`, `price × 100`;
        - `orders`: `order_id`, `customer_id`, `status`, `created_at` (мс), `updated_at` (мс);
        - `order_items`: `order_item_id`, `order_id`, `product_id`, `quantity`, `price_at_order × 100`;
        - `inventory`: `product_id`, `warehouse_id`, `quantity`, `updated_at` (мс).
      - `email` и `updated_at` клиентов и товаров в ClickHouse не попадают, и сверка их не покрывает.
    - **Проверка формата (4.10).** На одноразовых Postgres и ClickHouse одинаковые данные дают одинаковые бакеты во всех 5 таблицах (`NULL`/`''`, кавычки, кириллица, `0.10`, микросекунды); мутации `NULL` как `\N`, без `reverse`, время в мкс ломают тест. На живых данных 2026-10-02 все 5 таблиц сошлись до бакета: Spark отбрасывает микросекунды в `DateTime64(3)`, отпечаток в мс верен.
    - **Почему не по `version`.** В Postgres нет LSN строки, сравнивать можно только содержимое.
  - **Образ Airflow.** `airflow/Dockerfile` от `apache/airflow:3.1.0` (та же версия, что на memtest) с `clickhouse-connect`, версия закреплена явно (или из constraints Airflow 3.1.0, если пакет там есть). Собирается на Pi5 `docker compose build`: у Pi5 есть доступ к apt/pip, registry не нужен. `airflow/` добавляется в список `rsync` ADR-0007. В 4.5 проверяется, а не предполагается: `airflow providers list` в образе содержит `fab` и `postgres`, нужен ли `airflow fab-db migrate`.
  - **Аутентификация UI и API.** FAB auth manager (`apache-airflow-providers-fab`), admin создаёт `airflow-init` из `AIRFLOW_ADMIN_USER`/`AIRFLOW_ADMIN_PASSWORD`. `SimpleAuthManager` из memtest — для разработки: пароли генерируются в файл, `all_admins` пускает без логина. Память api-server с FAB перепроверяется в 4.6 против лимита 768m (пик на memtest 302 МБ).
  - **Состав и память Pi5.** `airflow-db` (`postgres:17-alpine`, 256m), `airflow-init` (одноразовый: миграции + admin), `airflow-api-server` (768m), `airflow-scheduler` (1152m), `airflow-dag-processor` (512m). Triggerer не запускаем: deferrable-операторов нет, сенсор работает в `reschedule`. Лимиты и `parallelism` 2 из ADR-0004 не меняются. Тома на HDD через `data-root` Docker (ADR-0002). Порт только `${PI5_HOST}:8080` (ADR-0003). Сверка и DQ тянут агрегаты и ключи нескольких бакетов, бюджет задачи ~340 МБ проверяется нагрузкой 4.15.
  - **Подключения и секреты.** `AIRFLOW_CONN_SHOPFLOW_POSTGRES` и `AIRFLOW_CONN_SHOPFLOW_CLICKHOUSE` собираются в compose из переменных `.env` Pi5, а не хранятся в метабазе. Пароли генерируются URL-safe (`openssl rand -hex 24`), иначе URI ломается.
  - **Пользователь ClickHouse `airflow_reader`.**
    - Ходит по сети compose на `clickhouse:8123`, не через LAN. Подсеть сети compose на Pi5 закрепляется в текущем значении (4.5), у пользователя `HOST IP '${PI5_COMPOSE_SUBNET}'`.
    - `SELECT` на `raw_events`, `stg_*`, журналы, `stg_order_status_history`, `dim_*`, `fact_orders`, витрины и `dq_check_results`; `SELECT(database, table, partition, rows, bytes_on_disk, active, min_time, max_time)` на `system.parts`; `INSERT` только в `dq_check_results`. Без `ALTER`, `OPTIMIZE`, `DROP`: ретеншн исполняет TTL, DAG его проверяет.
    - Профиль без `readonly` (`readonly = 2` запрещает и `INSERT`), права — только грантами. Ограничения через constraints: `max_memory_usage = 536870912 MAX 536870912`, `max_execution_time = 120 MAX 120`, `max_threads = 2 MAX 2`: `FINAL` и MD5 по ~2 млн строк не должны отнимать CPU у вставок Spark и refresh.
  - **Таблица `dq_check_results`.** `ReplacingMergeTree(checked_at)`, `ORDER BY (dag_id, run_id, check_name, table_name)`: повтор задачи перезаписывает свою строку. Служебная таблица, а не «одна строка Postgres», поэтому версия здесь `checked_at`, а не LSN (ADR-0006 её не касается). Колонки: `dag_id`, `run_id`, `logical_date Nullable(DateTime64(6, 'UTC'))` (у ручного запуска Airflow 3 его может не быть), `check_name`, `table_name`, `status Enum8('ok', 'violation', 'lagging', 'source_unavailable', 'error')`, `pg_value Nullable(Int128)`, `ch_value Nullable(Int128)`, `violations UInt64`, `cutoff Nullable(DateTime64(6, 'UTC'))`, `details String` (JSON с примерами ключей), `checked_at DateTime64(6, 'UTC')`. Без TTL (NFR-5: агрегаты без ограничения). Её читает дашборд M5.
  - **Логи Airflow.** Сами не чистятся: DAG ретеншна удаляет логи задач и делает `airflow db clean` старше 30 дней.
  - **Алерты.** FR-11 — в M5. В M4 `on_failure_callback` пишет в лог задачи; Telegram подключается к нему позже без правки DAG. Статус `failed` значит «нужен человек»: `mismatch`, `lagging`, `error`, два дня `source_unavailable`.
- **Рассмотренные варианты:**
  - **SSH-туннель Pi5 → ноутбук.** Postgres остаётся на `127.0.0.1`, но на Pi5 появляется ключ к ноутбуку, на ноутбуке нужен `sshd`. Поверхность атаки больше, чем у роли только с SELECT с одного IP.
  - **WireGuard/Tailscale ноутбук ↔ Pi5.** Стабильный адрес в любой сети и шифрование, сверка работала бы вне дома. Лишний сервис и внешняя зависимость; ADR-0003 этот вариант отложил, вернуться при необходимости.
  - **Сверка на ноутбуке** (скрипт пишет агрегаты PG в ClickHouse). Сеть не меняется, но теряется стрелка AF → PG из PRD 6 и появляется второй планировщик.
  - **Публикация на `0.0.0.0` + фильтр в `DOCKER-USER`.** Не зависит от адреса ноутбука, но нужны постоянные правила iptables на ноутбуке; без них порт открыт в любой сети.
  - **`"userland-proxy": false` в `daemon.json` ноутбука** вместо `ip_nonlocal_bind`. Bind не нужен, но меняется публикация на `127.0.0.1` для всех проектов Docker на ноутбуке. Оба варианта действуют на весь хост; sysctl проще откатить.
  - **Override-файл compose для LAN-порта.** Легко забыть при запуске, и сверка молча станет `source_unavailable`.
  - **IP в `pg_hba.conf` в git как исключение из ADR-0003.** Проще, но расходится с правилом «IP только через `.env»`.
  - **Повторная проверка бакетов с той же `T` вместо арбитража по ключу.** На горячих таблицах через 10 минут в пути уже другие ключи: ложный `failed` почти каждый день.
  - **Исключение «горячих» ключей списком с обеих сторон.** Нужен второй запрос к PG после ClickHouse, изменения между запросами снова дают гонку; арбитраж проще и точнее.
  - **`track_commit_timestamp` и сравнение по времени коммита.** Точнее отсечка (`pg_xact_commit_timestamp(xmin)` против `event_time`), но рестарт PG и грант на функцию; арбитража по ключу достаточно.
  - **Сверка `count(*)` без отсечки.** Ложные расхождения каждый день.
  - **Выгрузка пар `(pk, h)` целиком в Python.** Не помещается в бюджет задачи при ~2 млн позиций за 2 недели.
  - **Retry задачи вместо сенсора.** Занимает слот на время ожидания и требует ручной классификации `try_number`.
  - **`SimpleAuthManager`.** Легче, но не для постоянной работы.
  - **Сборка образа на ноутбуке под arm64 (buildx + QEMU) и `docker save | ssh docker load`.** Без интернета на Pi5, но медленная эмуляция и лишний ручной шаг.
- **Последствия:**
  - Postgres на ноутбуке виден в LAN. Защита: одна строка `pg_hba` для IP Pi5, роль только с SELECT и read-only, `reject` для остальных, суперпользователь с LAN не пускается.
  - TLS на Postgres не включён: пароль защищает SCRAM, но данные сверки (агрегаты и ключи) идут по Wi-Fi открыто. Для домашней LAN принято; при переходе на WireGuard вопрос закрывается.
  - В чужой сети с той же адресацией ноутбук может получить тот же адрес, тогда порт открыт в чужой LAN. Защита там — только `pg_hba /32` и пароль `recon_reader`.
  - VPN `amn0` не должен перехватывать LAN: в 4.2 `ip route get ${PI5_HOST}` показывает `dev wlo1`, kill-switch не режет входящие из LAN.
  - Сверка находит расхождения строк, не менявшихся в PG последние 15 минут. Более свежие отклонения — это задача NFR-3 и статуса `lagging`, а не FR-8.
  - Сумма хешей по бакету — не криптографическая проверка, но решение принимает арбитраж по ключу, а бакеты только сужают поиск.
  - Каноническая строка — точка риска. Одинаковое форматирование в PG и CH проверяет тест на временных базах (4.10), иначе каждая строка будет «разной».
  - Окно ожидания ~2 часа и расписание 20:00 меняются в DAG без нового ADR.
  - `.env.example` ноутбука: `LAPTOP_HOST`, `LAPTOP_COMPOSE_SUBNET`, `RECON_READER_PASSWORD`, `CLICKHOUSE_AIRFLOW_PASSWORD` и `PI5_COMPOSE_SUBNET` (`create-ch-users.sh` запускается с ноутбука). `pi5.env.example`: `LAPTOP_HOST`, `RECON_READER_PASSWORD`, `CLICKHOUSE_AIRFLOW_PASSWORD`, `PI5_COMPOSE_SUBNET`, `AIRFLOW_FERNET_KEY`, `AIRFLOW_JWT_SECRET`, `AIRFLOW_DB_PASSWORD`, `AIRFLOW_ADMIN_USER`, `AIRFLOW_ADMIN_PASSWORD`. Пароли `POSTGRES_PASSWORD` и `DEBEZIUM_PASSWORD` на Pi5 не попадают.
- **Приёмка:** шаги 4.2–4.6 и 4.11 плана M4 в `docs/STATUS.md`. Для 4.2 дополнительно: `SELECT client_addr FROM pg_stat_activity WHERE usename = 'recon_reader'` = IP Pi5; после рестарта PG коннектор Debezium `RUNNING` и `scripts/check_pipeline.sh` зелёный.
- **История для интервью:** сверка двух баз без общего порядка событий — отсечка по одним часам, отпечатки по бакетам как фильтр и арбитраж по ключу вместо `count(*)`; «источник недоступен» отделён от «данные разошлись» и от «пайплайн отстаёт», чтобы выключенный ноутбук не будил алертами, а ошибка пароля не пряталась за ним.
