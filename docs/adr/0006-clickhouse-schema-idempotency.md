# ADR-0006: Схема ClickHouse: ключи и версии для идемпотентности и SCD2

- **Статус:** принято (2026-09-26), ревью `architect`: принять с правками, правки внесены.
- **Контекст:** NFR-4 требует, чтобы повторная доставка события не дублировала строку. Spark читает Kafka с гарантией at-least-once: после рестарта батч может записаться повторно. Debezium тоже at-least-once: после аварийной остановки Connect события повторяются с новыми оффсетами Kafka. Схема из PRD 5.2 этого не обеспечивает:
  - `raw_events` (MergeTree, `ORDER BY (topic, event_time)`) не содержит позиции события, повторная запись даёт дубль;
  - в `dim_customers` и `dim_products` версией служит `valid_from`, и он же входит в `ORDER BY`. Закрытие версии SCD2 (та же строка с `valid_to` и `is_current = 0`) имеет тот же `valid_from`, и ReplacingMergeTree не может выбрать, какая строка новее;
  - в `fact_orders` не определён источник `version`, и строка собирается из двух таблиц Postgres (`orders`, `order_items`).
  Таблицы создаются в M1 без данных, поэтому поменять схему сейчас дешевле всего.
- **Решение:**
  - База `shopflow`. Все метки времени в UTC: `DateTime64(3, 'UTC')`, для `valid_from` и `valid_to` `DateTime64(6, 'UTC')`.
  - **Версия = `source.lsn` Debezium (UInt64), но только для таблиц, где строка ClickHouse соответствует одной строке одной таблицы Postgres.**
    - В pgoutput `source.lsn` — это LSN записи WAL самого изменения, а не коммита.
    - Для одной строки он монотонен: блокировка строки не даёт второй транзакции записать изменение до коммита первой.
    - Между разными строками и таблицами LSN изменения порядок коммитов не задаёт, поэтому версии из разных таблиц не сравниваются.
  - **`raw_events`:**
    - колонки `topic`, `kafka_partition UInt32`, `kafka_offset UInt64`, `source_lsn UInt64`, `event_key String`, `event_time DateTime64(3, 'UTC')` (из `source.ts_ms`), `op`, `payload`, `ingested_at`;
    - движок `ReplacingMergeTree`, `ORDER BY (topic, kafka_partition, kafka_offset, source_lsn)`, `PARTITION BY toYYYYMMDD(event_time)`, `TTL event_time + INTERVAL 30 DAY`, `ttl_only_drop_parts = 1`.
    - `event_time` — время коммита в Postgres, а не время чтения, поэтому повтор от Spark попадает в ту же партицию и схлопывается.
    - `source_lsn` в ключе нужен на случай потери тома Kafka или пересоздания топика: оффсеты начинаются с 0, и без LSN новое событие с тем же оффсетом молча заменило бы старое.
    - Ключ по оффсету гасит только повторы Spark. Повторы Debezium — это другие сообщения, они остаются в `raw_events` и схлопываются в `stg_*`/`dim_*` по LSN.
  - **Staging вместо денормализованного факта:**
    - `stg_orders` (`ORDER BY order_id`) и `stg_order_items` (`ORDER BY order_item_id`), движок `ReplacingMergeTree(version, is_deleted)`, `version` = LSN изменения, `is_deleted UInt8` для DELETE.
    - `fact_orders` строится поверх них в M3 (представление или refreshable MV с JOIN по `order_id`). В M1 не создаётся.
    - Так не нужна общая версия для двух топиков, размножение события `orders` на позиции и состояние «заказ → позиции» в Spark.
  - **SCD2 (`dim_customers`, `dim_products`):**
    - движок `ReplacingMergeTree(version)`, `ORDER BY (<id>, valid_from)`, `valid_from` из `source.ts_us`, `version` = LSN события, которое последним записало строку;
    - закрытие версии перезаписывает строку с тем же ключом и большим LSN.
  - **Правила обработчика SCD2** (реализация в M3):
    - Перед генерацией пар «закрыть / открыть» события одного ключа в батче схлопываются по `(id, source.ts_us)` до максимального LSN. Версия с `valid_from`, равным новому, не закрывается. Иначе несколько UPDATE в одной транзакции дают закрытие и открытие с одинаковой версией, и строки с `is_current = 1` может не остаться.
    - DELETE закрывает текущую версию (`valid_to` = время удаления, `is_current = 0`), новая версия не открывается.
    - `op=r` (повторный снапшот) открывает новую версию, только если атрибуты отличаются от текущей.
    - Откуда берётся `valid_from` текущей версии (состояние Spark, чтение из ClickHouse по ключам батча или `before.updated_at`), решается в ADR на M3. `before.updated_at` годится, только если приложение обновляет `updated_at` при каждом UPDATE. Сейчас в 5.1 это `DEFAULT` при INSERT, и `now()` — время начала транзакции.
  - PRD 5.2 переписывается под эту схему, DDL лежит в `clickhouse/ddl/`.
- **Рассмотренные варианты:**
  - Версия = `ts_ms`: понятнее человеку, но неуникальна и зависит от часов.
  - Денормализованный `fact_orders` с версией `max(LSN компонентов)`: UPDATE `order_items` с меньшим LSN, пришедший после UPDATE `orders`, проигрывает и теряется навсегда; при равных версиях результат зависит от порядка вставки.
  - Версия = оффсет Kafka: при одной партиции порядок совпадает с порядком коммитов, включая снапшот. Но ломается при пересоздании топика без очистки ClickHouse.
  - Оставить `raw_events` на MergeTree и дедуплицировать в Spark: не спасает от повторной записи батча после рестарта.
  - `valid_to` без Nullable, со «вечной» датой: чуть быстрее, но менее очевидно при чтении. Оставляем Nullable, как в PRD.
- **Приёмка (1.8–1.10):**
  - `sqlfluff lint clickhouse/ddl` чистый.
  - Двойная загрузка тех же событий в `raw_events` после `FINAL` даёт исходное число строк.
  - Две версии одной строки `stg_order_items` после `FINAL` дают одну строку со старшей версией.
  - Строка с `is_deleted = 1` и старшей версией после `FINAL` исчезает.
- **Последствия:**
  - Чтение свежих данных через `FINAL` или `argMax` (конвенция `clickhouse-ddl`). `FINAL` по `raw_events` только с фильтром по `event_time`: без него на Pi5 упираемся в CPU (ADR-0004).
  - **Снапшот под нагрузкой:** у всех `op=r` один LSN (точка согласованности слота). Изменение, начатое до создания слота, может получить меньший LSN и проиграть устаревшей строке `op=r`. Правило: генератор на время первого снапшота остановлен (ADR-0005).
  - **Лаг между топиками:** `orders` и `order_items` приходят в Spark без общего порядка. Проверка FR-9 «осиротевшие позиции» и сверка FR-8 смотрят только строки старше окна лага (например, 10 минут).
  - **Воронка FR-5** требует меток времени переходов статусов. Её строим из `raw_events` или отдельной таблицы событий статусов, а не из последнего статуса в `stg_orders`.
  - Конвенция `clickhouse-ddl` дополняется `DateTime64(6, 'UTC')` для `valid_from`.
- **История для интервью:**
  - почему версия — LSN изменения, а не время, и почему её нельзя сравнивать между таблицами;
  - почему факт собирается из нормализованного staging, а не денормализуется в стриме;
  - как ReplacingMergeTree закрывает версии SCD2 без UPDATE и где ломается при нескольких изменениях в одной транзакции.
