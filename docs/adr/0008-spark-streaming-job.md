# ADR-0008: Spark Structured Streaming: топология, sink, отказы

- **Статус:** принято (2026-09-27), ревью `architect`: принять с правками, правки внесены.
- **Контекст:** M2 строит мост Kafka (ноутбук) → ClickHouse (Pi5). Контракт событий задан ADR-0005: полный конверт Debezium в JSON без схем, 1 партиция на топик, ретеншн 7 дней или 1 ГиБ на топик. Ключи и версии задаёт ADR-0006: `raw_events` по позиции Kafka (+ LSN), `stg_*` по PK с версией = `source.lsn`. Доставка at-least-once, идемпотентность на стороне ClickHouse (NFR-4). NFR-3: задержка до 5 мин. NFR-6: Kafka буферизует, пока Spark или Pi5 недоступны. Ресурсы ноутбука: 14 ГБ RAM (стек M1 ограничен 3,5 ГиБ), ~28 ГБ свободного диска. CPU Pi5 — узкое место (ADR-0004). Pi5 в сети по Wi-Fi и может пропасть без разрыва соединения. Условия входа из M1: writer ClickHouse для Spark (ADR-0007), подписка без heartbeat-топика (ADR-0005), чекпойнт на постоянном томе.
- **Решение:**
  - **Граница M2/M3.** В M2 Spark пишет `raw_events`, `stg_orders` и `stg_order_items`: это upsert по LSN без состояния. SCD2 (`dim_*`), `fact_orders`, MV и генерация `products`/`order_items`/`inventory` остаются в M3. PRD, раздел 10, обновляется. Дозаливка `dim_*` за прошлый период в M3 делается из `raw_events` (хранятся 30 дней, в Kafka ≤ 7 дней); способ фиксирует ADR на M3.
  - **Размещение.** Сервис `spark` в `docker-compose.laptop.yml`, образ из `spark-jobs/Dockerfile`.
    - Spark 4.0.4 (Scala 2.13, Java 17, Python 3), `local[2]`, драйвер 1 ГиБ, `mem_limit` 2g, `restart: unless-stopped`, `logging` с `max-size`/`max-file` (цикл рестартов не должен забить диск).
    - Jar-файлы (`spark-sql-kafka-0-10_2.13`, коннектор ClickHouse и клиент той версии, что в POM коннектора) скачиваются при сборке образа с проверкой sha256, а не через `--packages` при старте.
    - Kafka по `kafka:29092`, ClickHouse по `http://${PI5_HOST}:8123`.
    - UTC везде: `TZ=UTC`, `-Duser.timezone=UTC` для драйвера, `spark.sql.session.timeZone=UTC`. Spark UI публикуется только на `127.0.0.1:4040`.
  - **Топология: один запрос.**
    - `readStream` с `subscribe` на явный список из 5 топиков `cdc.public.{customers,products,orders,order_items,inventory}`: heartbeat-топики (включая возможный `cdc.public.debezium_heartbeat`, ADR-0005) и новые топики молча не подхватываются. `startingOffsets=earliest` (действует только без чекпойнта), `failOnDataLoss=true`, `maxOffsetsPerTrigger=20000`.
    - `trigger(processingTime="30 seconds")`, чекпойнт на именованном томе `spark-checkpoint`. `down -v` для стека ноутбука запрещён (runbook).
    - `foreachBatch`: батч кешируется; 1) все события пишутся в `raw_events`; 2) события `orders` и `order_items` разбираются и пишутся в `stg_*`; пустые DataFrame не пишутся; в конце `unpersist()`.
    - Повтор батча корректен: Spark фиксирует диапазон оффсетов в `offsets/` до выполнения и после рестарта переигрывает тот же `batchId` с тем же диапазоном. Если записан `raw_events`, а `stg_*` нет, повтор схлопнет raw и допишет stg. Частичная вставка внутри таблицы тоже безопасна.
  - **Разбор в Spark.**
    - **`raw_events`:** общий для всех таблиц разбор только `source.lsn`, `source.ts_ms`, `op`, без схем таблиц. `topic`, `partition`, `offset` из источника Kafka; `event_key` и `payload` как строки без изменений. `ingested_at = current_timestamp()` батча в Spark: часы те же, что у Postgres (ноутбук), поэтому расхождение часов Pi5 не попадает в метрику NFR-3, а вставка не зависит от поддержки DEFAULT в DSv2. В лаг не входит время самой вставки (секунды). При повторе батча строка с тем же ключом перезаписывается, и `ingested_at` становится временем повтора: это свойство метрики.
    - **`stg_*`:** `from_json` с явной схемой конверта на таблицу (ADR-0005). В stg идут только `op in (c, u, d, r)`; `r` обрабатывается как `c` (ADR-0006). Для `c`/`u`/`r` значения из `after`. Для `d` PK из ключа сообщения, остальные поля из `before` с `coalesce` к значениям по умолчанию: при `is_deleted=1` они не важны, а удаление не должно зависеть от REPLICA IDENTITY. `version` = `source.lsn`; `decimal` из строки в `Decimal(10,2)`, `timestamptz` из ISO в UTC.
    - **Схлопывание внутри батча:** на PK одна строка через `max_by(struct, struct(lsn, kafka_offset))`, а не `dropDuplicates`. У повторов Debezium LSN одинаковый, и развязка по оффсету делает результат детерминированным. Корректность между батчами обеспечивает `ReplacingMergeTree(version, is_deleted)`, а не Spark. Схлопывание идёт после карантина: если самая новая версия PK в батче ушла в карантин, в `stg_*` пишется последняя валидная, то есть `stg_*` отстаёт от `raw_events` по этому ключу, пока событие не перезальют. Это принятое поведение (ревью M2), расхождение находит сверка FR-8.
  - **Политика ошибок данных («ядовитые» события).** Детерминированная ошибка при рестарте повторяется, поэтому рестарт от неё не спасает.
    - **`raw_events`: fail-fast.** Событие без `source.lsn`, `source.ts_ms` или `op` нарушает контракт ADR-0005. Батч падает с ключом и оффсетом события в логе. Runbook: разобраться с источником, затем рестарт.
    - **`stg_*`: карантин.** Строка, у которой после разбора null в обязательном поле (PK, `version`, NOT NULL колонки Postgres) или значение вне диапазона типа ClickHouse, в stg не пишется. Она остаётся в `raw_events`, в лог батча пишется счётчик и первые ключи. Расхождение stg с Postgres находит сверка FR-8 (M4), дозаливка из `raw_events`. Так ошибка схемы одной таблицы не останавливает все топики и не рвёт буфер NFR-6.
  - **Sink: официальный коннектор ClickHouse** `com.clickhouse.spark:clickhouse-spark-runtime-4.0_2.13` (DataSource V2, HTTP).
    - Версия 0.10.1 (fat jar со встроенным `client-v2` 0.9.5), прошла spike 2.4.
    - Каталог `clickhouse` настраивается в коде из env, запись через `df.writeTo("clickhouse.shopflow.<table>").append()`. `spark.clickhouse.write.batchSize` ≥ `maxOffsetsPerTrigger`, чтобы не дробить вставку.
    - Встроенные ретраи коннектора закрывают короткие сбои сети. Повтор вставки безопасен (NFR-4).
    - **Таймауты сокета обязательны:** `option.connection_timeout` 10 с и `option.socket_timeout` 120 с в каталоге. Без них пропавший из Wi-Fi Pi5 даёт вечное зависание батча вместо ошибки. Spike 2.4: хост, не отвечающий на SYN, даёт падение через 40 с (4 попытки клиента по 10 с); сервер, принявший соединение и молчащий, — через 120 с (ошибку чтения клиент не повторяет).
    - **Коннектор не проверяет значения** (spike 2.4): `NULL` в не-Nullable `UInt64` записывается как `0`, `-1` — как `18446744073709551615`, без ошибки. Поэтому проверки fail-fast (raw) и карантина (stg) делает Spark до записи, на отказ ClickHouse полагаться нельзя.
    - **Запасные варианты** (если spike 2.4 не пройдёт): 1) `clickhouse-jdbc` через `df.write.jdbc` (`socket_timeout`) на том же Spark 4.0.4; 2) `foreachPartition` + HTTP `INSERT ... FORMAT JSONEachRow`, как в `scripts/load_sample_events.sh`. Не зависит от совместимости коннектора, но сериализацию и таймауты пишем сами.
  - **Отказы.**
    - **Временный сбой ClickHouse:** ретраи коннектора → батч падает → процесс выходит с ненулевым кодом → Docker перезапускает контейнер. Docker сбрасывает задержку рестарта, если контейнер проработал больше 10 с, а старт Spark дольше. Поэтому entrypoint до запуска запроса ждёт `GET /ping` ClickHouse с backoff (5 с, удвоение, потолок 60 с; потолок 5 мин добавлял до 2 мин к простою, сценарий 2.9 B) и логирует ожидание. Без этого был бы цикл «JVM → батч → падение» раз в 20–40 с. Ретраев внутри батча в коде нет.
    - **Зависание:** watchdog-поток в драйвере завершает процесс (`os._exit(1)`), если за 10 мин не было ни `onQueryProgress`, ни `onQueryIdle` (`StreamingQueryListener`). `onQueryIdle` приходит и при отсутствии новых данных, поэтому простой генератора не считается зависанием. Тот же listener обновляет файл-маркер, по которому Docker healthcheck показывает `unhealthy`. Это для наблюдения: сам Docker не перезапускает `unhealthy`, перезапуск делает watchdog.
    - **Простой дольше буфера Kafka:** запрос падает на `failOnDataLoss`. Восстановление ручное (runbook): рестарт с `failOnDataLoss=false`, затем сверка FR-8.
    - **Потеря чекпойнта:** запрос читает с `earliest`, повторы схлопываются по ключам ADR-0006.
    - **Потеря тома Kafka при живом чекпойнте:** оффсеты чекпойнта больше конца топика, запрос падает на `failOnDataLoss`. Runbook: удалить том `spark-checkpoint`, повторы гасит ключ с LSN (ADR-0006).
    - Consumer group в Kafka не используется: позиции только в чекпойнте, `kafka.group.id` не задаём.
  - **Writer ClickHouse.** Пользователь `spark_writer` создаётся идемпотентным скриптом с ноутбука (`scripts/create-ch-users.sh`) до первого запуска Spark.
    - `IDENTIFIED WITH sha256_hash`: хеш считается локально, пароль не попадает ни в git, ни в `query_log`. Пароль лежит в `CLICKHOUSE_SPARK_PASSWORD` в `.env` ноутбука.
    - Права: `INSERT, SELECT` на `shopflow.raw_events`, `shopflow.stg_orders`, `shopflow.stg_order_items`; `SELECT` на `system.clusters` и `system.macros`. Spike 2.4: при загрузке каталога коннектор читает топологию (`system.clusters`, `system.macros`), а схему таблицы в `loadTable` — через `SELECT` всех колонок. `system.tables`, `system.columns`, `system.databases` ClickHouse отдаёт с фильтром по правам, отдельный грант не нужен.
    - `HOST IP` берётся из переменной подсети LAN, IP в коде не зашит (ADR-0003).
    - Отдельный профиль с `max_memory_usage` 512 МиБ: вставка не должна конкурировать со слияниями в бюджете 2 ГБ (ADR-0004).
    - Пароль передаётся в Spark через env контейнера и читается в коде. В `--conf` и командной строке его нет; Spark UI скрывает ключи с `password` (`spark.redaction.regex`).
    - Принятые риски: пароль виден через `docker inspect` (как в ADR-0005) и уходит по HTTP в LAN открытым текстом (как у `shopflow`).
  - **Типы.** `stg_order_items.quantity` меняется с `UInt32` на `Int32`, как `INT` в Postgres. Иначе отрицательное количество ушло бы в карантин или переполнилось, и проверка FR-9 «нет отрицательных сумм» его бы не увидела. Таблица на Pi5 пустая, поэтому пересоздаётся (2.3). PRD 5.2 обновляется.
- **Рассмотренные варианты:**
  - Spark 4.2 + JDBC: новее, но у коннектора нет сборки под 4.1/4.2. Выбираем 4.0.4 (поддерживается, релиз 2026-07) с коннектором. JDBC остаётся запасным путём, Spark менять не нужно.
  - Отдельный запрос на каждый топик: изоляция отказов, но 5 чекпойнтов и 5 консьюмеров на 2 ядрах. От отказа sink он не изолирует (sink общий), а отказы из-за данных закрывает политика карантина.
  - Два запроса (raw и stg) из одного источника: raw продолжает копиться при ошибке в stg. Нужен только при fail-fast для stg, а выбран карантин.
  - `subscribePattern` `cdc\.public\..*`: подхватил бы `cdc.public.debezium_heartbeat`, если его добавят по ADR-0005.
  - `ingested_at` через DEFAULT `now64()` в ClickHouse: в лаг входит вставка, но расхождение часов Pi5 и ноутбука попадает прямо в NFR-3, а DSv2 может требовать все колонки.
  - Fail-fast для stg: ошибка схемы одной таблицы останавливает все топики, и за время починки уходит буфер Kafka.
  - Разбор конверта в ClickHouse (MV поверх `raw_events`): логика уезжает на CPU Pi5 и хуже тестируется. Противоречит цели проекта (streaming-опыт на Spark) и ADR-0005 («схему задаёт Spark»).
  - Kafka engine в ClickHouse: без Spark, и Kafka пришлось бы открыть в LAN.
  - Spark на Pi5: не помещается в бюджет 6 ГБ (ADR-0004).
  - `trigger(availableNow)` по расписанию Airflow: меньше ресурсов, но это уже микробатч по cron, а не стрим. Запасной вариант, если ноутбук будет перегружен.
  - Trigger по умолчанию (батч сразу за батчем): много мелких вставок, на Pi5 растёт число партов. 30 с — компромисс с NFR-3.
  - `collect()` на драйвер и вставка по HTTP из Python: не масштабируется. Путь через `foreachPartition` выше масштабируется по партициям.
- **Приёмка (2.2–2.9):**
  - Batch-чтение 5 топиков возвращает все сообщения по `kafka-get-offsets`.
  - От `spark_writer` `INSERT` проходит, а `DROP` и `CREATE` дают `ACCESS_DENIED`.
  - Spike (пройден 2026-09-27): вставка без изменения DDL (DEFAULT `ingested_at` работает, явный тоже); `DateTime64(3,'UTC')` из ISO с микросекундами и `Z` (усечение до мс, партиция по UTC); LSN больше 2^53 без потерь; null и отрицательные значения в `UInt*` записываются молча (см. выше); права коннектора найдены; недоступный хост и молчащий сервер дают ошибку по таймауту, а не зависание.
  - После догона `raw_events FINAL` по каждому топику = число позиций в Kafka; события, залитые вручную в 1.10, схлопнулись.
  - `stg_orders FINAL` без удалённых = `count(*)` в Postgres при остановленном генераторе; два UPDATE одной строки в одной транзакции дают старшую версию; «ядовитое» событие в `order_items` уходит в карантин, остальные топики пишутся.
  - p95 и максимум `ingested_at - event_time` меньше 5 мин под нагрузкой генератора (без окон сценариев отказа).
  - Сценарии: `SIGKILL` Spark; остановка ClickHouse на 5 мин; «сетевая чёрная дыра» (DROP в `DOCKER-USER` на Pi5); `down`/`up` ноутбука; повторы Debezium. После каждого сверки сходятся.
- **Последствия:**
  - **Буфер NFR-6 = min(7 дней, 1 ГиБ / суточный объём топика)**, а не 7 дней. Замер 2026-09-27: `cdc.public.orders` ≈ 880 байт на событие, при `--rate 5` (~4 события `orders`/с) это ≈ 320 МБ в сутки, 1 ГиБ заполнится за ~3,4 дня. Замер 2.8 (30 мин, `--rate 5 --no-seasonality`): `orders` 313 МиБ в сутки, 1 ГиБ за 3,3 дня; `customers` 60 МиБ в сутки (17 дней); остальные топики пока без потока. Штатный режим генератора (`--rate 2` × сезонность, средний множитель 0,83) даёт ~104 МиБ в сутки, 1 ГиБ за ~9,8 дня: буфер ограничен временем, 7 дней. **Решение (2026-09-27): `retention.bytes` не меняем.** Нагрузочные прогоны `--rate 5` явно принимают буфер ~3,5 дня. Пересмотреть в M3, когда генератор начнёт писать `order_items` и `inventory`. **Пересмотрено 2026-09-29 (M3, 3.4), решение то же:** см. ADR-0009, «Последствия».
  - **Память ноутбука:** сумма `mem_limit` стека 5,5 ГиБ из 14.
  - **Диск ноутбука:** образ Spark ~1,5 ГБ, чекпойнт — десятки МБ (`minBatchesToRetain` 100 по умолчанию), логи ограничены ротацией.
  - **Вставки в ClickHouse:** до 3 INSERT на батч раз в 30 с, ≈ 8600 в сутки. На каждую таблицу один парт в 30 с, фоновые слияния справляются.
  - **Догон после простоя:** 20000 событий на батч; неделя при 5 событиях/с (~3 млн) — ~150 батчей, не меньше ~75 мин из-за интервала trigger.
  - **Эволюция схемы:** новая колонка в Postgres молча теряется `from_json` в `stg_*`, но остаётся в `payload` `raw_events` (ADR-0005). Новая NOT NULL колонка, которой нет в схеме Spark, не ломает разбор. Несовпадение типа даёт карантин, а не остановку. Схема в коде меняется вместе с DDL.
  - **Лаг между топиками** `orders` и `order_items` не устраняется: они в одном батче, но без общего порядка (ADR-0006). Сверки смотрят строки старше окна лага.
  - **Генератор M1 почти не пишет в `order_items`:** `stg_order_items` в M2 проверяется ручным DML.
- **История для интервью:**
  - почему один запрос с `foreachBatch`, а не запрос на топик, и почему повтор батча безопасен;
  - где проходит граница ответственности: Spark разбирает, ClickHouse дедуплицирует по версии;
  - временная ошибка против детерминированной: рестарт с ожиданием, карантин, fail-fast по контракту;
  - почему падение лучше зависания: таймауты сокета и watchdog;
  - почему буфер Kafka меряется в байтах, а не только в днях;
  - почему Spark 4.0, а не последний (совместимость коннектора важнее новизны).
