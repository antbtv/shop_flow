# ADR-0009: SCD2, факт заказов и дневные витрины

- **Статус:** принято (2026-09-29), ревью `architect`: принять с правками, правки внесены (4 блокера, 7 желательных). Заменяет правила обработчика SCD2 из ADR-0006 («Правила обработчика SCD2»): закрытие версии перезаписью строки больше не используется, `dim_*` целиком строит refreshable MV.
- **Контекст:** M3 закрывает FR-3 (SCD2 для `customers` и `products`), FR-4 (выручка по дням и категориям), FR-5 (воронка created → paid → delivered) и строит `fact_orders` поверх `stg_*` (ADR-0006). ADR-0006 оставил открытым, откуда обработчик SCD2 берёт `valid_from` текущей версии, чтобы её закрыть. Ограничения:
  - Доставка at-least-once: повторы батча Spark и повторы Debezium с тем же LSN (ADR-0006, ADR-0008). События разных топиков приходят без общего порядка, батч может быть переигран, дозаливка приносит старые события после новых.
  - Spark stateless, `foreachBatch`, чекпойнт можно потерять (runbook), после чего поток перечитывает Kafka с `earliest`.
  - Единственный порядок, монотонный для строки Postgres, — LSN изменения (ADR-0006). `source.ts_us` — часы ноутбука: шаг NTP назад или выход из сна могут перевернуть его относительно LSN. Повторный снапшот (`op=r` после потери слота, ADR-0005) приходит со старшим LSN и временем снапшота.
  - CPU Pi5 — узкое место, `max_server_memory_usage` ClickHouse 2 ГБ (ADR-0004). Разбор конверта Debezium делает Spark, а не ClickHouse (ADR-0008).
  - Объём через 2 недели при штатном режиме генератора (`--rate 2` × 0,83, ~40 % действий — новые заказы): ~0,8 млн заказов и ~2 млн позиций. Клиентов и товаров — тысячи, версий — десятки тысяч.
  - Первые события лежат в Kafka с 2026-09-26 и уйдут из неё около 2026-10-03; в `raw_events` они хранятся 30 дней.
- **Решение:**
  - **SCD2: журнал версий из Spark, измерение пересчитывает ClickHouse, порядок — по LSN.**
    - Spark пишет каждое изменение строки `customers`/`products` в `stg_customer_versions` / `stg_product_versions`: `(<id>, valid_from, <атрибуты>, is_snapshot, is_deleted, event_time, version)`. `valid_from` = `source.ts_us` (`DateTime64(6, 'UTC')`, время коммита), `version` = `source.lsn`, `is_snapshot` = `op = 'r'`, `event_time` = `source.ts_ms`. Движок `ReplacingMergeTree(version)`, `ORDER BY (<id>, valid_from)`. `is_deleted` здесь не параметр движка: строка удаления нужна, чтобы закрыть версию.
    - Ключ `(id, valid_from)` схлопывает несколько UPDATE одной транзакции (один `ts_us`, побеждает старший LSN), повторы Debezium (тот же LSN) и повтор батча. Внутри батча Spark делает то же своей функцией: `max_by` по `(lsn, kafka_offset)` в группе `(id, ts_us)`. `latest_per_key` (группа только по PK) для журналов не годится: она сжала бы историю ключа до одной строки.
    - Если два разных коммита одной строки получат один `ts_us` (практически невозможно: строка заблокирована, точность — микросекунды), промежуточная версия теряется. Принято.
    - `op=d`: строка с `is_deleted = 1`, атрибуты из `before` со значениями по умолчанию, как в `stg_*`.
    - `dim_customers` / `dim_products` (таблицы ADR-0006, схема не меняется) — цели refreshable MV `dim_customers_mv` / `dim_products_mv`, полный пересчёт с атомарной заменой содержимого. Таблицами владеет MV: прямые записи в `dim_*` стираются следующим refresh.
    - Запрос MV, три шага, все окна `PARTITION BY <id> ORDER BY version ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` (без явной рамки `leadInFrame` в ClickHouse не видит следующую строку):
      1. `FINAL` по журналу; сравнение кортежа `(<атрибуты>, is_deleted)` с `lagInFrame` того же кортежа; строки без изменений отбрасываются. Так `op=r` без изменений и UPDATE, не затронувший атрибуты измерения (`email`, `updated_at`), не открывают версию, а вставка после удаления не склеивается с удалённой версией.
      2. Отдельным подзапросом над оставшимися строками: `valid_to = leadInFrame(toNullable(valid_from))` (без `toNullable` последняя строка получила бы `1970-01-01`, а не NULL).
      3. Строки удаления отбрасываются (они только закрыли предыдущую версию), `is_current = valid_to IS NULL`, `version` = LSN строки версии. Первая строка ключа с `is_snapshot = 1` получает `valid_from = 1970-01-01`: снапшот описывает строку, существовавшую до него, и заказы старше снапшота находят её в `ASOF JOIN`.
    - Атрибуты версии: `customers` — `name`, `address`, `segment`; `products` — `name`, `category`, `price`.
    - Порядок прихода событий не важен: пересчёт идёт по всему журналу, опоздавшее событие встаёт на своё место по LSN.
  - **Воронка: история статусов из Spark, первое время перехода.** `stg_order_status_history`: `(order_id, status, changed_at DateTime64(3, 'UTC'), is_snapshot, version)`, `ReplacingMergeTree(version)`, `ORDER BY (order_id, status, version)`. Строка пишется для `op=c`/`op=r` (статус при вставке) и для `op=u`, где `before.status IS DISTINCT FROM after.status`; UPDATE без смены статуса строку не даёт. `changed_at` = `source.ts_ms`. Повторы Debezium схлопываются по LSN. Витрина берёт `min(changed_at)` по `(order_id, status)`: реальный переход не перетирается ни повторным снапшотом (старший LSN, позднее время), ни повтором статуса. Внутри батча Spark схлопывает по `(order_id, status, lsn)`.
    - «Дошёл до статуса» считается монотонно по порядку жизненного цикла: `delivered` означает `shipped` и `paid`, даже если строки промежуточного статуса нет (заказ пришёл снапшотом в финальном статусе).
  - **`stg_inventory`:** последнее состояние `inventory`, `ReplacingMergeTree(version, is_deleted)`, `ORDER BY (product_id, warehouse_id)`, как `stg_*` ADR-0006. `StgSpec` расширяется до составного PK (ключ сообщения содержит обе колонки). Нужен для FR-7 (M5) и сверки.
  - **`event_time` в staging.** `stg_orders`, `stg_order_items`, `stg_inventory` и журналы получают `event_time DateTime64(3, 'UTC')` = `source.ts_ms` последнего записавшего события (миграция `ADD COLUMN` для существующих таблиц). Нужен для окна лага в FR-8/FR-9 (M4: «сироты» и расхождения старше 10 мин) и для водяного знака витрин. Старые строки заполняет дозаливка: версия та же, при равной версии RMT оставляет последнюю вставку.
  - **Точность времени заказа.** `stg_orders.created_at` переводится в `DateTime64(6, 'UTC')` (миграция `MODIFY COLUMN`, Debezium отдаёт микросекунды). Иначе заказ, начатый в ту же миллисекунду, что коммит смены цены, после усечения окажется раньше `valid_from`, и `ASOF JOIN` выберет старую цену. `created_at` — начало транзакции заказа (`now()`); для последовательного генератора это позже коммита любой предыдущей смены цены.
  - **`fact_orders`: представление, зерно — позиция заказа.**
    - `stg_order_items FINAL` `INNER JOIN` `stg_orders FINAL` по `order_id`, затем `ASOF LEFT JOIN dim_products` по `product_id` и `created_at >= valid_from`, `SETTINGS join_use_nulls = 1` (промах ASOF даёт NULL, а не `''`/`0`). Если 25.8 не примет разный масштаб `DateTime64` в условии ASOF, типы приводятся явно (проверка в 3.5).
    - Колонки: `order_item_id`, `order_id`, `customer_id`, `product_id`, `status`, `created_at`, `order_date`, `quantity`, `price_at_order`, `amount = quantity * price_at_order`, `category`, `list_price`.
    - `INNER JOIN` скрывает позиции без заказа, поэтому DQ (FR-9, M4) читает `stg_*`, а не `fact_orders`. Проверка «дубли по ключу заказа» после `FINAL` всегда даёт 0: DQ смотрит `stg_*` без `FINAL` по `(ключ, version)` или `raw_events`.
    - Представление, а не таблица: свежесть без лишнего звена refresh. Читают его refreshable MV витрин и представления FR-6/FR-7 в M5 (агрегаты, не построчный дашборд). Порог перехода на refreshable MV в таблицу `MergeTree`: p95 refresh витрин больше половины периода в замере 3.12 или представления M5 делают пересчёт факта чаще раза в период.
  - **Витрины: refreshable MV с полным пересчётом**, таблицы `MergeTree` без версий (содержимое заменяется атомарно, при ошибке refresh остаётся старое):
    - `mart_revenue_daily`: `order_date`, `category`, `orders`, `items`, `revenue` (сумма `amount`), `revenue_net` (без `cancelled`). День — по UTC `created_at`.
    - `mart_funnel_daily`: по дню создания заказа — `created`, `paid`, `shipped`, `delivered`, `cancelled` (дошли до статуса, монотонно), медиана и p90 времени created → paid и paid → delivered.
    - В обеих: `refreshed_at` и `source_watermark` = `max(event_time)` источников на момент пересчёта. Задержка витрины = `now() - source_watermark`, ею меряется NFR-3 в 3.12.
    - Инкрементальные MV (триггер на INSERT) отклонены: вставка в `ReplacingMergeTree` — это и обновления, и повторы, агрегат посчитал бы их дважды.
    - Запасной путь при росте объёма: пересчёт последних N дней с `APPEND` в `ReplacingMergeTree` по `(order_date, category)` с версией = время refresh.
  - **Расписание: одна цепочка, пересчёты не пересекаются.** Все MV `REFRESH EVERY 2 MINUTE`: `dim_customers_mv` и `dim_products_mv` без зависимостей, `mart_revenue_daily_mv DEPENDS ON dim_products_mv`, `mart_funnel_daily_mv DEPENDS ON mart_revenue_daily_mv` (зависимость ради очерёдности, а не данных). Витрина не пересчитывается раньше измерения, и две витрины не держат память одновременно. `SETTINGS refresh_retries = 3`. Стенд 3.5: при создании зависимая MV ждёт (`WaitingForDependencies`); в плановом цикле зависимая MV стартовала через 3034 мс после старта 3-секундного refresh зависимости, то есть после его окончания. Пересчёты цепочки не пересекаются.
  - **Задержка витрин, худший случай:** trigger 30 с + батч ~3 с + ожидание refresh `dim_products_mv` до 2 мин + его длительность + длительность витрины (оценка ≤ 20 с) ≈ 3 мин, внутри NFR-3 (5 мин). Замер 3.12 по `source_watermark`. `stg_*` и журналы — ~30 с, как в M2.
  - **Права и ресурсы.**
    - `spark_writer`: `INSERT, SELECT` на `stg_customer_versions`, `stg_product_versions`, `stg_order_status_history`, `stg_inventory` (SELECT нужен коннектору, ADR-0008). На `dim_*`, `fact_orders` и витрины прав нет.
    - Refreshable MV создаёт `shopflow` с `SQL SECURITY DEFINER`. Стенд 3.5: refresh без `APPEND` пишет во временную таблицу и подменяет TO-таблицу через `EXCHANGE` (UUID `dim_customers` меняется), поэтому определителю нужны `SELECT, INSERT, CREATE TABLE, DROP TABLE ON shopflow.*` (ошибка `ACCESS_DENIED` у урезанного пользователя). Отдельный определитель с такими правами почти равен владельцу базы, выигрыша нет: определитель — `shopflow`. Права на `dim_*` и витрины выдаются по имени и переживают подмену. У таблицы может быть только одна refreshable MV (`BAD_ARGUMENTS` на вторую): `dim_*` принадлежат ровно одной MV.
    - В запросах MV `SETTINGS max_memory_usage` 512 МиБ для `dim_*`, 768 МиБ для витрин, `max_threads = 2`. С цепочкой в каждый момент идёт не больше одного пересчёта: 768 МиБ + вставка Spark 512 МиБ + слияния укладываются в 2 ГБ (ADR-0004).
  - **Дозаливка истории: Spark batch из `raw_events`.**
    - `spark-jobs/backfill_from_raw.py`: читает `raw_events` через каталог `clickhouse` (у `spark_writer` уже есть `SELECT`) с фильтром по `topic` и дням `event_time` и пропускает строки через те же функции разбора и схлопывания журналов, что и поток. Пишет журналы, историю статусов, `stg_inventory` и заново `stg_orders`/`stg_order_items` (заполняет `event_time`). Повтор безопасен (ключи выше), параллельно с потоком тоже.
    - Запуск тем же образом через `docker compose run` с `mem_limit`, по дням. В 3.8 проверяется по `query_log` на Pi5, что фильтр доходит до ClickHouse; если нет — `payload` за 30 дней пойдёт по Wi-Fi целиком, и фильтр выносится в запрос каталога.
    - Не зависит от ретеншна Kafka и не требует сброса чекпойнта. Тот же скрипт закрывает «дозаливку из `raw_events`» после карантина (ADR-0008). История старше 30 дней в журнал не попадёт; для стенда доступна вся (с 2026-09-26).
  - **Генератор (M3):** товары (засев, изменения цены, редкая смена категории), 1–5 позиций в одной транзакции с заказом по текущей цене, остатки по складам (засев, списание при заказе, пополнение), `updated_at = now()` при каждом UPDATE. Действия идут последовательно, по одной транзакции, поэтому `price_at_order` = `list_price` в `fact_orders` для всех его заказов: сквозная проверка SCD2 (3.9).
- **Рассмотренные варианты:**
  - Spark читает текущую версию из `dim_*` по ключам батча и пишет пару «закрыть/открыть» (исходный план ADR-0006): `SELECT ... FINAL` на каждый батч, чтение после записи без гарантии слияния, повтор батча после частичной записи видит уже открытую версию, опоздавшее событие в середину истории не вставить без пересчёта.
  - Состояние в Spark (`transformWithState`): состояние живёт в чекпойнте, а его потеря — штатная процедура runbook; после неё история строится только с начала Kafka (≤ 7 дней).
  - Порядок окна по `valid_from`: проще читать, но часы ноутбука могут перевернуть его относительно LSN, и текущей станет устаревшая версия.
  - Ключ журнала `(id, version)` со схлопыванием транзакции в MV через `argMax` по `(id, ts_us)`: журнал совсем не зависит от часов, но хранит все UPDATE транзакции, и правило ADR-0006 уезжает в SQL. Ключ `(id, ts_us)` с порядком по LSN даёт то же при одном допущении (разные коммиты — разный `ts_us`).
  - `valid_to` на лету в представлении `dim_*`: `ASOF JOIN` пересчитывал бы окна при каждом refresh витрин; таблица с десятками тысяч версий дешёвая.
  - `valid_from` из `before.updated_at`: зависит от дисциплины приложения и отсутствует для `op=d`.
  - `fact_orders` сразу как refreshable MV в `MergeTree`: `FINAL` и джойн один раз за цикл, предсказуемые пики памяти, но +1 звено задержки и 2 млн строк на HDD. Запасной путь, порог выше.
  - Денормализация факта в Spark: отклонена в ADR-0006.
  - История статусов с ключом `(order_id, status)`: повторный снапшот и повтор статуса перезаписывают время реального перехода.
  - Воронка из последнего статуса `stg_orders` (теряет время переходов) или из `raw_events` через `JSONExtract` в ClickHouse (разбор на CPU Pi5, ADR-0008).
  - Дозаливка сбросом чекпойнта: кода нет, но ручной шаг с удалением тома и история в пределах ретеншна Kafka.
  - День витрины по `Europe/Moscow`: ближе к бизнесу, но расходится с конвенцией «всё в UTC». Переход в M5, если понадобится.
- **Проверки стенда (3.5, 2026-09-30, временный ClickHouse 25.8.33.6 на ноутбуке с конфигами Pi5):**
  - Прототип `dim_customers_mv` на журнале, залитом дважды (повтор Debezium): клиент с INSERT, UPDATE, двумя UPDATE одной транзакции, UPDATE без смены атрибутов и DELETE даёт версии A, B, D (C схлопнута ключом, UPDATE без изменений не версия), последняя закрыта временем удаления, текущей нет; снапшот открывает первую версию с 1970-01-01, повторный снапшот с теми же атрибутами версию не даёт; часы назад: по LSN текущей остаётся верная версия, `valid_to < valid_from` находит ключ.
  - ASOF: смена цены в 10:05:00.000400, заказ в 10:05:00.000900 — с `DateTime64(6)` `list_price` = новой цене, с усечением `created_at` до мс — старой (блокер ревью подтверждён). Разный масштаб `DateTime64(3)`/`(6)` в условии ASOF 25.8 принимает. `join_use_nulls = 1`: промах даёт NULL.
  - Воронка: `min(changed_at)` сохраняет реальное время оплаты при повторном снапшоте статуса; заказ из снапшота в `delivered` считается `paid` и `shipped`. День воронки берётся из `stg_orders.created_at`, а не из первой строки истории (для снапшота это время снапшота).
  - Spark-коннектор после миграций 011/012: запись `stg_orders` без `event_time` (текущий job) проходит, колонка получает DEFAULT; с `event_time` тоже; `created_at` сохраняет микросекунды. Миграции можно применять на Pi5 до выкатки нового job.
  - Оконное выражение над агрегатом: `max(max(event_time)) OVER ()`, а не `max(event_time) OVER ()` (`NOT_AN_AGGREGATE`).
- **Приёмка (3.5–3.12):**
  - `sqlfluff lint clickhouse/ddl` чистый; миграции и гранты применяются повторно без ошибок. На стенде (3.5): права определителя и атомарность refresh с TO-таблицей, `DEPENDS ON` в цепочке, ASOF с `DateTime64(3)`/`(6)`, результаты записаны сюда.
  - Тесты Spark: два UPDATE в одной транзакции дают одну строку версии со старшим LSN; история ключа из нескольких транзакций в одном батче сохраняется целиком; переход статуса пишет строку истории, UPDATE без смены статуса — нет; повтор Debezium схлопывается; составной PK `inventory`.
  - На Pi5 (3.8): одна `is_current = 1` на живой ключ, их число = `count(*)` в Postgres, атрибуты совпадают; разрывов и перекрытий нет; в порядке LSN `valid_from` не убывает; `op=r` без изменений не даёт версии.
  - `fact_orders` (строки старше 10 мин): число строк и сумма `amount` = Postgres; строк с `price_at_order ≠ list_price` для заказов генератора M3 — 0; промахов ASOF (NULL `category`) — 0.
  - Витрины совпадают с запросами к Postgres по дням старше окна лага; `system.view_refreshes`: ошибок нет, пересчёты не пересекаются.
  - Нагрузка 30 мин `--rate 5` (3.12): `LoadAverage1` и RSS ClickHouse в рамках ADR-0004, парты не растут, p95 `now() - source_watermark` < 5 мин.
- **Последствия:**
  - `dim_*` отстают от журнала версий до ~2 мин, витрины от `stg_*` — до ~2,5 мин.
  - Полный пересчёт и `FINAL` по непартиционированным `stg_*` растут линейно с объёмом; замер 3.12 решает, нужен ли пересчёт окна или таблица для факта.
  - **Объём Kafka с генератором M3 (замер 3.4, 2026-09-29, 30 мин `--rate 5 --no-seasonality`):**
    | Топик | Байт на событие | МиБ/сутки `--rate 5` | До 1 ГиБ, дней | МиБ/сутки штатно | До 1 ГиБ штатно, дней |
    | --- | --- | --- | --- | --- | --- |
    | `inventory` | 874 | 400 | 2,6 | 133 | 7,7 |
    | `order_items` | 780 | 347 | 2,9 | 115 | 8,9 |
    | `orders` | 900 | 284 | 3,6 | 94 | 10,9 |
    | `customers` | 1025 | 48 | 21 | 16 | 64 |
    | `products` | 953 | 11 | 95 | 4 | 285 |
    Штатный режим = `--rate 2` × средняя сезонность 0,83 = 0,332 от `--rate 5`. Самый тяжёлый топик теперь `inventory` (списание на каждую позицию, `REPLICA IDENTITY FULL` удваивает событие), а не `orders`.
    - **Решение: `retention.bytes` 1 ГиБ не меняем.** В штатном режиме все топики держат 7 дней (буфер NFR-6 = 7 дней), запас у `inventory` 10 %: изменение весов генератора в сторону заказов или пополнений его съест, пересчитать при правке `ACTION_WEIGHTS`. Нагрузочные прогоны `--rate 5` явно принимают буфер ~2,6 дня (было 3,3 в M2).
    - Диск Kafka: штатно ~2,5 ГиБ за 7 дней; худший случай при долгом `--rate 5` — 5 топиков × (1 ГиБ + сегмент 256 МиБ) ≈ 6,3 ГиБ. На ноутбуке 2026-09-29 свободно 12 ГБ (было 26 ГБ в M1, место заняли образы Docker и файлы вне ShopFlow, тома ShopFlow ~125 МБ). Увеличение `retention.bytes` отклонено из-за диска; держать свободными ≥ 10 ГБ.
  - Если Spark стоит, `dim_*` и витрины просто не меняются; застой виден по `source_watermark`. Ошибки refresh — в `system.view_refreshes` (алерт — M5).
  - Журналы версий и история статусов без TTL (NFR-5: измерения и агрегаты хранятся без ограничения).
  - PRD 5.2 дополняется новыми таблицами; тип `segment` выравнивается с DDL (`LowCardinality(String)`).
- **История для интервью:**
  - почему SCD2 собирается пересчётом из журнала версий, а не read-modify-write в стриме, и как это даёт идемпотентность и терпимость к порядку событий;
  - почему порядок версий — LSN, а не время коммита, и почему история статусов хранит первое время перехода;
  - почему инкрементальная MV поверх ReplacingMergeTree считает неверно, и когда полный пересчёт дешевле инкремента;
  - `ASOF JOIN` как point-in-time join факта к SCD2-измерению, точность времени и сквозная проверка через `price_at_order`;
  - где проходит граница: Spark разбирает события и пишет журналы, ClickHouse собирает модель.
