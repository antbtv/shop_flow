# ADR-0012: Исходящий канал Pi5 → Telegram через туннель AmneziaWG

- **Статус:** принято с условием (2026-10-03), ревью `architect`: принять с правками (7 блокеров B0–B6, 5 желательных). Условие B0 (нативный конфиг для отдельного устройства из подписки) выполнено; туннель установлен на Pi5 и проверен (5.11, 2026-10-03): живое сообщение доставлено, отказ туннеля проверен, пункты приёмки 1–3, 6, 7 пройдены; пункты 4, 5, 8 (`reboot`, обрыв Wi-Fi, `amn0`) перенесены в 5.14.
- **Контекст:** FR-11 требует алертов в Telegram, их шлёт callback в контейнере `airflow-scheduler` (ADR-0011). Живая проверка 5.11 показала: с Pi5 `api.telegram.org`, `core.telegram.org` и `149.154.166.110` по IPv4 дают таймаут, IPv6 маршрута нет, `example.com` отвечает (200). Сеть Pi5 блокирует Telegram (не DNS, не Docker, не `DOCKER-USER`). У пользователя есть подписка Amnezia Premium (протокол `awg`, несколько устройств); ключ `vpn://` содержит только `api_config` и `api_key`, готового конфига нет.
- **Решение:**
  - **Хостовый туннель AmneziaWG с узкими маршрутами.** Демон `amneziawg-go` (userspace: модуля ядра для `6.18.50+rpt-rpi-2712` нет, DKMS сломался бы при обновлении ядра) и `awg`, `awg-quick`; юнит `awg-quick@awg0`. В `AllowedIPs` только IPv4-диапазоны Telegram (`core.telegram.org/resources/cidr.txt`, 9 префиксов), без `0.0.0.0/0` и `::/0`: default route, остальной трафик Pi5 и Docker не меняются, контейнеры идут через хост без правок compose и кода.
  - **Конфиг (B1).** Нативный конфиг AmneziaWG, выгруженный из приложения Amnezia для НОВОГО устройства (не ноутбучного: один ключ с двух адресов рвёт оба туннеля). Правки только такие: `AllowedIPs` как выше, без `DNS=` (иначе DNS хоста и Docker уйдёт к провайдеру VPN), только IPv4 в `Address`, `MTU = 1280`, `PersistentKeepalive = 25`. Шаблон: `infra/pi5/etc/amnezia/awg0.conf.example`.
  - **Секрет (B6).** Реальный конфиг на Pi5 `/etc/amnezia/amneziawg/awg0.conf`, `root:root 600`, каталог `700`; на ноутбуке только в приватной папке вне репозитория. В git только шаблон, `.gitignore` закрывает `infra/pi5/etc/amnezia/*.conf` и `build/`. `rsync`-список ADR-0007 `/etc` не затрагивает. Установщик отказывается ставить конфиг с `DNS=`, `Table=`, плейсхолдером, IPv6 или диапазоном вне Telegram и стирает промежуточную копию.
  - **Вход через туннель закрыт (B2).** В `DOCKER-USER` (`after.rules`) после `ESTABLISHED,RELATED RETURN`: `-i awg0 -m conntrack --ctstate NEW -j DROP`. Без него пакет из `awg0` на `$PI5_HOST:8123` проходил бы DNAT Docker, а фильтр ADR-0003 смотрит только `-i wlan0`: порты ClickHouse, Airflow и Grafana были бы доступны тому, кто управляет сервером VPN.
  - **MTU и MSS (B3).** `PostUp`/`PostDown` ставят и снимают `TCPMSS --clamp-mss-to-pmtu` на `FORWARD -o awg0`: у туннеля MTU 1280, у bridge 1500, без этого TLS из контейнера виснет при рабочем `curl` на хосте. Приёмка из контейнера scheduler, не с хоста.
  - **Автозапуск (B5).** Юнит `After=`/`Wants=network-online.target`, `Restart=on-failure`, `RestartSec=30`, `WG_ENDPOINT_RESOLUTION_RETRIES=infinity`: `oneshot` без повтора навсегда остался бы `failed`, если Wi-Fi или DNS поздно.
  - **Доставка бинарников.** У Pi5 нет GitHub (ADR-0007), для Debian 13 пакета нет: `scripts/pi5/build-awg.sh` собирает на ноутбуке в контейнере `golang:1.25-bookworm` статические `linux/arm64`, источники закреплены тегом и полным коммитом (`amneziawg-go` v3.1.20260828 `b5928efb…`, `amneziawg-tools` v3.1.20260812 `ee0f0a9a…`), `SHA256SUMS` проверяет `install-awg.sh` на Pi5.
  - **Обнаружение отказа (B4).** Туннель может молча перестать работать (подписка, смена endpoint, провайдер блокирует протокол, сменились адреса Telegram), а DAG-и останутся зелёными. Плановый DAG `shopflow_alert_channel` (`40 */3 * * *` МСК) из контейнера scheduler делает GET без токена на `TELEGRAM_API_URL`: любой HTTP-ответ (включая 5xx) — `ok`, таймаут и отказ — `error`: проба проверяет сетевой путь до Bot API, а не токен и chat id (отозванный токен или чужой chat id она не видит, панель останется зелёной, это осознанно: токен не покидает scheduler и не участвует в пробе); пишет `telegram_reachable` в `dq_check_results`; callback только `log_failure` (канал не алертит через себя). Панель 32: часов с последней успешной проверки, оранжевая > 5, красная > 7, 99999 — проверок не было.
- **Рассмотренные варианты:**
  - Sidecar-туннель с `network_mode: service:` для scheduler: весь Airflow зависит от жизненного цикла VPN-контейнера (NFR-6), `NET_ADMIN`, лимит из оставшихся ~256 МиБ ADR-0004. Хуже хостового.
  - Sidecar-ретранслятор и `TELEGRAM_API_URL`: токен открытым текстом по bridge, ещё один образ и `mem_limit`.
  - Обратный прокси на своём сервере: у пользователя нет сервера вне блокировки; прокси видит токен.
  - Другой канал (e-mail, ntfy): меняет формулировку FR-11; запасной вариант, если подписка не отдаст нативный конфиг.
  - Ретрансляция через ноутбук: отклонено принципиально, алерт «второй подряд `source_unavailable`» возникает как раз при выключенном ноутбуке (NFR-6).
  - Туннель на весь трафик Pi5: весь трафик и DNS через провайдера VPN, ломает локальную сеть.
- **Приёмка (на Pi5, команды выполняет пользователь):**
  1. `ip route get 149.154.166.110` — `dev awg0`; `ip route get 1.1.1.1` — `dev wlan0`; `ip route show default` и nameserver'ы в `resolv.conf` не изменились.
  2. Из контейнера `airflow-scheduler`: GET без токена на `https://api.telegram.org/` возвращает HTTP-код; `shopflow_data_quality` с `simulate_violation=true` — сообщение пришло; штатный запуск — тишина; токена в логах 0 (`alerts-smoke.sh`).
  3. `sudo iptables -S DOCKER-USER` содержит `-i awg0 ... NEW -j DROP`; `sudo iptables -t mangle -S FORWARD` — TCPMSS; `sudo ss -tlnp` — порты только на `$PI5_HOST`.
  4. После `sudo reboot` без ручных действий юнит `active`, handshake моложе 3 минут, пункт 2 проходит.
  5. Обрыв Wi-Fi на минуту: через 3 минуты пункт 2 проходит.
  6. `systemctl stop awg-quick@awg0`: проба пишет `error`, панель 32 краснеет, `simulate_violation` пишет `Telegram alert not delivered`, состояние задачи не меняется; после `start` проба снова `ok`.
  7. `stat -c '%U:%G %a'` конфига — `root:root 600`; `git ls-files | grep -i -e awg -e amnezia` — только шаблон, скрипты и юнит.
  8. Ноутбучный туннель `amn0` стабилен при поднятом туннеле Pi5.
- **Проверено локально (ноутбук):** `scripts/pi5/test-awg-local.sh` — два контейнера с настоящим AmneziaWG (amd64-сборка тех же исходников), клиентский конфиг собран из шаблона: Telegram-диапазон идёт через `awg0`, `1.1.1.1` и default route остаются, `resolv.conf` не тронут, MTU 1280, TCPMSS ставится и снимается, HTTP на «Telegram» (`149.154.166.110`) проходит через туннель, handshake есть. `tests/test_awg_template.py` (7) и `tests/test_install_awg.py` (19) — шаблон, юнит, правило `DOCKER-USER`, установщик без root. На Pi5 проверено позже (см. STATUS 5.11): нативный конфиг нового устройства Premium содержит параметры AmneziaWG 2.0 (`S3`, `S4`, `I1`, …), `awg-quick` и `amneziawg-go` arm64 работают, Telegram доступен с хоста и из контейнера scheduler.
- **Последствия:**
  - Исходящий канал Pi5 зависит от третьей стороны (провайдер VPN видит SNI `api.telegram.org` и время сообщений, токен и текст внутри TLS). Подписка кончилась или протокол заблокирован: алерты не уходят, об этом сообщает панель 32 (до 7 ч задержки), а не Telegram.
  - Алерт при недоступном канале по-прежнему теряется без очереди (ADR-0011); желательные D1–D3 `architect` (запись результата доставки, outbox, ежедневное «жив») — отдельной задачей.
  - Демон `amneziawg-go` живёт вне cgroup контейнеров, в резерве памяти ОС; RSS замерить в 5.12.
  - Модуль ядра не нужен: обновление ядра Pi туннель не ломает.
  - Как отозвать устройство: в приложении Amnezia удалить устройство подписки, на Pi5 `install-awg.sh uninstall`.
