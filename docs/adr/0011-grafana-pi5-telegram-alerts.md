# ADR-0011: Grafana на Pi5, витрины M5 и алерты Telegram

- **Статус:** принято (2026-10-03), ревью `architect`: принять с правками, правки внесены (8 блокеров, 16 желательных).
- **Контекст:** M5 закрывает FR-6, FR-7 (витрины), FR-10 (дашборд) и FR-11 (алерты). Ограничения:
  - PRD 13 закрыт пользователем 2026-10-03: Grafana на Pi5. Резерв под дашборд по ADR-0004 — 0,5 ГБ; сумма лимитов M4 2816 + 1152 + 768 + 512 + 256 = 5504 МиБ, с Grafana 384 МиБ — 5888 из 6144. Superset не берём: ≥ 1 ГБ и недоступность при выключенном ноутбуке (NFR-6).
  - Порты Pi5 публикуются только на `$PI5_HOST`; правило `DOCKER-USER` не привязано к порту (`infra/pi5/etc/ufw/after.rules.snippet`).
  - `fact_orders` — представление: чтение под ограниченным пользователем требует грантов и на базовые таблицы (так выдан `airflow_reader`). Дашборду нужны только витрины.
  - Узкое место Pi5 — CPU. Refresh цепочки витрин ≤ 1,3 с и 283 МиБ на 1 млн заказов (4.16), период 2 мин (ADR-0009).
  - Airflow 3.1: `on_failure_callback` задачи выполняется в процессе задачи (контейнер `airflow-scheduler`, LocalExecutor), если сбой поднят кодом задачи. Задачу, помеченную `failed` извне (heartbeat timeout, kill, возможно «Mark failed» в UI), обрабатывает dag-processor, где секретов нет (`conns=0`, ADR-0010).
  - `dq_check_results` — `ReplacingMergeTree(checked_at)`; запуск со статусом `source_unavailable` или `lagging` пишет только сводную строку (`shopflow_checks/outcome.py`).
  - Секреты только в `.env` (ADR-0007), порты — ADR-0003.
- **Решение:**
  - **Grafana на Pi5.**
    - `grafana/Dockerfile`: `grafana/grafana-oss` закреплённого тега (лучше digest) + плагин `grafana-clickhouse-datasource` закреплённой версии, zip `linux_arm64` с проверкой sha256. Плагин ставится в `GF_PATHS_PLUGINS=/opt/grafana/plugins`, вне тома: именованный том копирует содержимое образа только при создании, и после пересборки остался бы старый плагин. Сборка на Pi5, как у Airflow.
    - Без выхода в интернет при старте: `GF_PLUGINS_PREINSTALL_DISABLED=true`, `GF_ANALYTICS_REPORTING_ENABLED=false`, `GF_ANALYTICS_CHECK_FOR_UPDATES=false`, `GF_ANALYTICS_CHECK_FOR_PLUGIN_UPDATES=false`, `GF_SNAPSHOTS_EXTERNAL_ENABLED=false`, `GF_SECURITY_DISABLE_GRAVATAR=true`. Встроенные алерты Grafana выключены (`GF_UNIFIED_ALERTING_ENABLED=false`): канал алертов один, через Airflow.
    - Доступ: `GF_AUTH_ANONYMOUS_ENABLED=false`, `GF_USERS_ALLOW_SIGN_UP=false`, `GF_SECURITY_COOKIE_SAMESITE=strict`, защиту от перебора логина не выключаем. TLS нет, как у Airflow 8080: принимается для LAN.
    - Память: `mem_limit` 384m на сумму **двух процессов** (grafana-server и backend-плагин ClickHouse, отдельный Go-процесс в том же cgroup), `GOMEMLIMIT` ≈ 256MiB у сервера (плагин он может не ограничить). Пик обоих замеряется в 5.12; потолок — резерв 0,5 ГБ. В ADR-0004 добавляется строка Grafana.
    - Данные (SQLite, логи) на HDD (`grafana-data`), `restart: unless-stopped`, без `depends_on` на ClickHouse: Grafana поднимается и без него. Healthcheck `/api/health` тем инструментом, что есть в образе (`wget` или `curl`, проверяется в 5.5).
    - Порт `${PI5_HOST}:3000`. Новых правил файрвола не нужно: `DOCKER-USER` не зависит от порта, `ufw allow 3000` не нужен (DNAT обходит INPUT). `rules.md` и PRD 6.1 дополняются портом 3000.
    - Provisioning из git (`dashboards/`): источник данных `editable: false`, провайдер дашбордов `allowUiUpdates: false`, `disableDeletion: true`; правки только через git. Пароль источника подставляется через `$__env{}`.
    - Доставка: список `rsync` (ADR-0007) дополняется `grafana/` и `dashboards/`, `--delete` внутри них допустим.
  - **Секреты Grafana.** `GF_SECURITY_ADMIN_PASSWORD`, `GF_SECURITY_SECRET_KEY` (иначе пароль источника в SQLite шифруется публичным ключом по умолчанию) и пароль `grafana_reader` есть только в окружении сервиса `grafana` и в `.env`/`pi5.env.example` как плейсхолдеры (`GRAFANA_ADMIN_PASSWORD`, `GRAFANA_SECRET_KEY`, `CLICKHOUSE_GRAFANA_PASSWORD`). Пароль `grafana_reader` есть и в `.env` ноутбука для `create-ch-users.sh` (как `CLICKHOUSE_AIRFLOW_PASSWORD`). Значения hex (`openssl rand -hex 24`). `GF_SECURITY_ADMIN_PASSWORD` действует только при первом создании базы; смена — `grafana cli admin reset-admin-password` (runbook).
  - **Доступ к ClickHouse: `grafana_reader`.**
    - Создаётся `scripts/create-ch-users.sh`, `HOST IP` подсети compose Pi5, протокол `http`, порт 8123, хост `clickhouse`.
    - Гранты: SELECT только на `mart_revenue_daily`, `mart_funnel_daily`, `mart_cohort_retention`, `mart_top_products_daily`, `mart_inventory_current`, `mart_pipeline_health`, `dq_check_results`. Ни `stg_*`, ни `raw_events`, ни `fact_orders`, ни `dim_*`, ни `system.parts`: размеры таблиц дашборд берёт из строк `check_name = 'table_size'` в `dq_check_results` (их пишет `retention_dag.py`). Любой admin Grafana может выполнить произвольный SQL под этим пользователем, поэтому минимальные гранты — граница доверия.
    - Профиль: `readonly = 2` (плагин передаёт настройки в запросе, при `readonly = 1` падает), `max_memory_usage` 256 МиБ (MAX), `max_execution_time` 30 с (MAX), `max_threads` 2 (MAX), `max_rows_to_read` 20 млн, `read_overflow_mode = 'throw'`. Спилла на диск нет: порог равен лимиту памяти, а запись на HDD при обновлении каждые 30 с вредна; запрос падает быстро.
    - В provisioning источника `queryTimeout` 20 и `dialTimeout` 10 (стенд 5.5): драйвер плагина шлёт `max_execution_time` = время до дедлайна запроса + ~4–5 с (`queryTimeout` 20 уходит как 24, `dialTimeout` 10 как 14; `queryTimeout` 30 уходил как ~35 и давал `SETTING_CONSTRAINT_VIOLATION` на каждой панели и в проверке источника), поэтому оба значения держим минимум на 5 с ниже MAX профиля (30); число соединений ограничено (`maxOpenConns` 2, `maxIdleConns` 2: поля приняты плагином 4.22.0, влияние на параллельные панели не измерялось). Приёмка 5.5: в `system.query_log` (`Settings`) у запросов `grafana_reader` нет настроек выше MAX.
    - `GF_DASHBOARDS_MIN_REFRESH_INTERVAL=30s`; автообновление дашборда 1 мин (витрины обновляются раз в 2 мин, меньшее ничего не даёт).
  - **Витрины M5 — таблицы `MergeTree` под refreshable MV** (как M3, ADR-0009): `grafana_reader` читает только их, запросы панелей дешёвые.
    - **Расписание.** Период 2 мин, как у всей цепочки (при 5 мин худший случай задержки выходит за NFR-3). Линейный порядок через `DEPENDS ON`: `dim_products_mv` → `mart_revenue_daily_mv` → `mart_funnel_daily_mv` → `mart_cohort_retention_mv` → `mart_top_products_daily_mv` → `mart_inventory_current_mv` → `mart_pipeline_health_mv`. Все с `max_threads = 2`, `max_memory_usage` 768 МиБ. Если упал `dim_products_mv`, замирает вся цепочка, это видно по `source_watermark`.
    - **Отступление от порога ADR-0009.** Порог «переход `fact_orders` на таблицу, если представления M5 пересчитывают факт чаще раза в период» срабатывает буквально: факт читают `mart_revenue_daily_mv` и `mart_top_products_daily_mv`. Осознанно: проход факта 0,6–0,7 с и ≤ 181 МиБ на 1 млн заказов (4.16), цепочка последовательная. **Замер 5.3 на Pi5** (1 млн заказов, 3 млн позиций): сумма refresh цепочки из 8 MV 10,3 с, пик памяти 286 МиБ (витрины, лимит 768 МиБ), проход факта 0,9–1,4 с. Первоначальное условие «цепочка > 10 с» (взято до замера) формально превышено на ~0,8 с, но таблица факта сняла бы два прохода (~2–2,5 с) ценой собственного refresh (≥ 1,4 с), записи ~4 млн строк на HDD и ещё одного звена задержки: чистая выгода ≲ 1 с. Решение пользователя 2026-10-03: `fact_orders` остаётся представлением, порог перехода переформулирован: цепочка refresh больше 30 с (четверть периода 2 мин), или пик памяти refresh больше 600 МиБ, или `stg_order_items` больше ~4,5 млн строк (порог ADR-0009). Тогда `fact_orders` становится таблицей под refreshable MV в начале цепочки (+1 звено задержки до 2 мин, ~2 млн строк на HDD). Вторая причина следить: DQ 01 по ADR-0009 упирается в лимит `airflow_reader` около 4,5 млн позиций раньше всех.
    - `mart_cohort_retention` (FR-6). Источник — `stg_orders FINAL` (`customer_id`, `created_at`, `status`), без позиций и ASOF. Когорта — месяц (UTC) первого неотменённого заказа клиента. «Неотменённый» включает `created` и неоплаченные. Клиент, удалённый в Postgres, но с заказами, считается. Период — число месяцев от когорты, `returned` — клиенты с неотменённым заказом в этом периоде; в периоде 0 `returned = customers`, повторный заказ в том же месяце не возврат. Retention = `returned / customers`. Сетка полная (периоды 0..N с `returned = 0`, `customers` в каждой строке), иначе на тепловой карте дыры вместо нулей. `is_partial = 1` на диагонали, где `addMonths(cohort_month, period) = toStartOfMonth(now('UTC'))`.
    - `mart_top_products_daily` (FR-7). Зерно — день создания заказа × `product_id` × категория на момент заказа, как в `mart_revenue_daily`. Колонки: `product_name` (текущее имя из `dim_products` с `is_current`, иначе `'unknown'`: у `grafana_reader` нет гранта на `dim_*`), `quantity` и `revenue` без отменённых (и те же значения с отменёнными, отдельными колонками), `source_watermark`. Окна 7 и 30 дней панель считает суммой по дням; панель группирует по `product_id`, потому что при смене категории внутри дня строк две.
    - `mart_inventory_current` (FR-7). `stg_inventory FINAL` (`is_deleted = 0`) `LEFT JOIN dim_products` на `is_current = 1`, `join_use_nulls = 1`, `ifNull(category, 'unknown')`, как в `mart_revenue_daily_mv`. Колонки: товар, категория, склад, остаток, `is_low` (остаток < константы `LOW_STOCK_THRESHOLD` с комментарием, значение по данным генератора), `source_watermark` = `max(stg_inventory.event_time)`.
    - `mart_pipeline_health` (здоровье, NFR-3). Лёгкая refreshable MV: `max(event_time)` по каждой `stg_*` и состояние MV из `system.view_refreshes` (ошибки refresh видны на дашборде: закрывает отложенное в ADR-0009 «ошибки refresh — M5» визуально). Грантов на `stg_*` у `grafana_reader` нет; определитель MV — `shopflow`.
  - **Дашборд «ShopFlow».** Секции: выручка и воронка (FR-4, FR-5), когорты (FR-6), топ и остатки (FR-7), здоровье. Здоровье:
    - свежесть витрин `now() - source_watermark` и `mart_pipeline_health`;
    - статусы проверок из `dq_check_results FINAL`: сначала последний **плановый** запуск по `dag_id` (`startsWith(run_id, 'scheduled__')`, максимум `checked_at` сводной строки `table_name = ''`), затем строки этого `run_id` (иначе потабличные строки старого запуска выглядят текущими при `source_unavailable` и `lagging`); ручные запуски (`simulate_violation`) показываются отдельно с типом запуска;
    - **возраст последнего планового запуска по `dag_id`**, красная панель при > 26 ч: сторож самого Airflow (scheduler лёг, DAG не импортируется, Pi5 без интернета, задача помечена `failed` извне), дешёвая замена dead man's switch без токена в Grafana;
    - `table_size` из `dq_check_results`.
  - **Алерты Telegram (FR-11).**
    - Клиент `airflow/dags/shopflow_common/telegram.py`: stdlib `urllib`, таймаут 10 с, один повтор (верхняя граница callback ~2 × 10 с плюс DNS, `timeout` DNS не покрывает), без `parse_mode`, текст усекается до лимита Telegram. Токен в URL: исключение пересоздаётся `raise ... from None` (у `HTTPError` в цепочке `.url`/`.filename` содержат токен), в лог попадают только `type(exc).__name__` и HTTP-код, токен регистрируется в secrets masker Airflow (`mask_secret`; путь импорта в 3.1 проверяется на стенде). Тест 5.9 грепает весь лог задачи.
    - `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` только в окружении `airflow-scheduler`; в `.env` Pi5 их вносит пользователь вручную.
    - Два явных callback в `shopflow_common/callbacks.py`: `alert_failure` (лог + Telegram) и `log_failure` (только лог). Явное назначение, а не таблица «итоговая задача по `dag_id`»: новый DAG без записи не теряет и не дублирует алерты.
      - `shopflow_reconciliation`: `report` — `alert_failure`, остальные задачи — `log_failure`.
      - `shopflow_data_quality`, `shopflow_retention`: `alert_failure` (через `DEFAULT_ARGS`, у DAG одна падающая задача либо итоговая).
      - `shopflow_healthcheck`: только `log_failure` (ручной smoke-тест, две независимые задачи; `check_postgres` при выключенном ноутбуке падает с `SourceUnavailable`, это не алерт).
    - Алертят: `violation`, `lagging`, `error`, второй подряд `source_unavailable`, провал DQ и ретеншна. Не алертят: первый `source_unavailable` и `skipped` сенсор (`soft_fail`, callback не вызывается).
    - Текст: DAG, задача, `run_id`, статус, ссылка на UI (`AIRFLOW__API__BASE_URL`), не более 3 ключей-примеров, без паролей и строк подключения. Источник статуса и `details`: callback читает `dq_check_results FINAL` по `run_id`, при недоступном ClickHouse — откат на текст исключения. `report` явно проверяет состояния всех upstream-задач: любое `failed` даёт `error` (сейчас инвариант держится косвенно через XCom, добавляется тест).
    - Callback не пробрасывает исключения: сбой Telegram пишется в лог на уровне ERROR, состояние задачи не меняется.
    - **Проверено на стенде (Airflow 3.1.0, LocalExecutor, 5.10), где какой callback выполняется:**
      - исключение из кода задачи (`simulate_violation`): callback в процессе задачи (scheduler), сообщение уходит, токен ни в одном логе;
      - `kill -9` процесса задачи (supervisor пишет `exit_code=SIGKILL final_state=failed`): задача и запуск `failed`, **callback не выполняется нигде** (ни в задаче, ни в scheduler, ни в dag-processor), сообщения нет. Это строже, чем предполагал ADR: компенсация только панелью «возраст последнего планового запуска» (запись в `dq_check_results` не появится);
      - гибель supervisor (heartbeat timeout, на стенде 30 с): scheduler помечает задачу `failed`, callback выполняется в **dag-processor**, без токена и без соединения `shopflow_clickhouse` (`lookup_run` падает, откат на текст), `Telegram alert skipped` в логе, ничего не падает; callback пришёл дважды подряд (два запроса) — безвредно, пока у dag-processor нет токена, и ещё одна причина его не давать.
- **Рассмотренные варианты:**
  - Superset на ноутбуке: FR-10 пропадает при выключенном ноутбуке, ≥ 1 ГБ на ноутбуке с запасом Spark ~12 %.
  - Grafana читает `fact_orders` и `stg_*` напрямую: гранты на базовые таблицы, тяжёлые запросы на каждое обновление панели. Отклонено.
  - Алерты Grafana Alerting вместо Airflow-callback: покрывают «Airflow мёртв» и задачи, убитые извне, по `dq_check_results` и `source_watermark`. Отклонено: токен и исходящий интернет у сервиса, доступного из LAN, +50–100 МБ, два места с правилами. Роль сторожа выполняет панель возраста запусков.
  - Callback уровня DAG: выполняется в dag-processor без секретов; выдавать их туда расширило бы поверхность.
  - Провайдер Telegram или HTTP-hook Airflow: лишняя зависимость в образе и токен в подключении.
  - `fact_orders` сразу таблицей под refreshable MV: снимает порог ADR-0009, но добавляет звено задержки и ~2 млн строк на HDD. Замер 5.3 (цепочка 10,3 с, пик 286 МиБ) перехода не требует; условия пересмотра — в разделе «Решение».
  - Готовые окна «7 и 30 дней» в витрине: каждое окно — отдельный пересчёт. Отклонено, зерно по дням.
- **Приёмка (по задачам M5):** `sqlfluff lint clickhouse/ddl`; `pytest -q tests/sql` (когорты, топ, остатки, health); `grafana_reader`: `SHOW GRANTS` как выше, `ACCESS_DENIED` на `stg_*`, `raw_events`, `fact_orders`; в логе старта Grafana нет обращений к grafana.com, `grafana cli plugins ls` показывает закреплённую версию; `ss -tlnp` — 3000 только на `$PI5_HOST`; `oom_kill` 0 и Grafana в лимите под `--rate 5`; живое сообщение Telegram на `simulate_violation`; в 5.10 `kill -9` процесса задачи: в логе dag-processor callback отработал без токена и не упал.
- **Последствия:**
  - Три новые MV и `mart_pipeline_health` добавляют нагрузку на Pi5; замер в 5.2–5.3 и 5.12.
  - **Принятое ограничение:** задача, помеченная `failed` извне, не алертит; компенсация — панель возраста запусков. Алерт при недоступном Telegram или интернете Pi5 теряется без очереди (ERROR в лог), вторым каналом остаётся дашборд.
  - Когорты пересчитываются задним числом: если первый заказ клиента позже отменят, клиент переедет в более позднюю когорту.
  - Дашборды правятся через git, ручные правки в UI не сохраняются.
  - Фильтр `DOCKER-USER` действует на `-i wlan0`: при подключении Pi5 по Ethernet фильтра не будет (наблюдение к ADR-0003, не к M5).
  - Токен Telegram в `.env` Pi5 (ADR-0007), не в `rsync`.
- **Проверить на стенде, а не предполагать.** Закрыто в 5.5 (Grafana 12.4.3, плагин 4.22.0): плагин шлёт только `max_execution_time` (дедлайн + ~4–5 с, см. выше), остальные настройки приходят из профиля; `maxOpenConns` и `maxIdleConns` принимаются в `jsonData`; `GF_PLUGINS_PREINSTALL_DISABLED` работает (Grafana стартует healthy в сети без выхода наружу, плагин `valid`, `/var/lib/grafana/plugins` не создаётся); в образе есть `wget` и `curl` (healthcheck — `wget`); `grafana cli plugins ls` видит плагин только с `--pluginsDir /opt/grafana/plugins`. Закрыто в 5.9: `mask_secret` в Airflow 3.1 — `airflow.sdk.log.mask_secret` (старый `airflow.sdk.execution_time.secrets_masker` помечен устаревшим); после регистрации токен в строке `…/bot<token>/sendMessage` показывается как `***`. Остаётся на 5.10: где выполняется callback при heartbeat timeout в Airflow 3.1.
